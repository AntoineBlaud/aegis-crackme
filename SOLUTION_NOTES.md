# Aegis — solution notes (full spoilers)

Ground truth for the algorithm, used to write and verify the challenge
and to sanity-check any solve (a manual one, an MCP agent's, anyone's)
against the real answer. **If you want to attempt Aegis blind, stop
here** — this page and `tools/keygen.py` give away everything.

## The algorithm

Key = 8 bytes = 5-byte `serial` (free choice) + 3-byte `check`.

```
mac(serial5):
    block = serial5 + b"\x00\x00\x00"       # 8 bytes, check field zeroed
    cipher = feistel_encrypt(block, subkeys) # 8 rounds
    return cipher[0:3]

valid(key8) := key8[5:8] == mac(key8[0:5])
```

Feistel, 32-bit halves, little-endian:

```
L, R = block[0:4], block[4:8]      # both little-endian u32
for i in 0..7:
    L, R = R, L ^ F(R, subkeys[i])
cipher = L || R
```

Round function:

```
F(R, sk):
    x = rotl32(R ^ sk, 5)
    x = (x * 0x9E3779B1) mod 2^32
    x ^= (x >> 15)
    return x
```

Key schedule (runs host-side only — never inside the VM; the VM only ever
sees the 8 already-expanded subkeys as constant-pool entries):

```
MASTER_KEY = 0xC0FFEE42
subkeys[i] = rotl32(MASTER_KEY ^ (i * 0x2545F491), (i * 3) mod 32),  i = 0..7
```

Concretely:

```
subkeys = [0xC0FFEE42, 0x2DD0D69F, 0x9D01D822, 0x5C67E35E,
           0x83C0655E, 0x144BBD51, 0x54907D71, 0x36B882C8]
MIX_CONST = 0x9E3779B1
```

A correct solve needs to recover the 8 subkeys and `MIX_CONST` (both sit
directly in the VM's constant pool — `tools/vm.py`'s/`vm.c`'s
`consts[0..8]`) and the round-function shape (from tracing/decompiling
`checkpoint_vm_mac`'s VM program), NOT necessarily `MASTER_KEY` itself —
the schedule step is intentionally left out of scope (see README "what's
deliberately left easy").

## Known-good test keys

Generated by `tools/keygen.py`, verified against both `tools/proto.py`
(plain Python) and the actual compiled `build/aegis.exe` on 2026-09-20:

```
serial=DEMO1  ->  AEGIS-4445-4D4F-31E2-26A4
serial=HELLO  ->  AEGIS-4845-4C4C-4F1A-4997
serial=00000  ->  AEGIS-0000-0000-0096-EC83
```

Any 5-byte serial works — `python tools/keygen.py <text>` or
`python tools/keygen.py --hex <10 hex chars>` mints a fresh valid key for
it; `python tools/keygen.py --check <KEY>` verifies one.

## Verification already performed

- `tools/build_bytecode.py` ran the exact shipped bytecode program through
  `tools/vm.py`'s interpreter against 500 random valid keys (from
  `tools/proto.py`) and 500 of the same keys with one check-byte bit
  flipped: **0 mismatches** against the plain-Python oracle on all 1000.
- The C project was compiled with MSVC 14.41 (`/W4`, no warnings) and the
  resulting `build/aegis.exe` was run against: no args (usage, exit 1),
  `--dump-checksums` (matched the Python-computed FNV-1a values exactly:
  bytecode `0xFD20FF1F`, consts `0x18C991CD`), the known-good key above
  (accepted, exit 0), that same key with one bit flipped (rejected, exit
  1), a garbage string (rejected cleanly, no crash), and 5 more fresh
  random keys straight out of `tools/keygen.py` (all 5 accepted).
- `build/aegis.map` was checked to confirm `checkpoint_format`,
  `checkpoint_vm_mac`, `checkpoint_integrity`, `checkpoint_antidebug`, and
  `run_all_checkpoints` all survive as separately named, non-inlined
  symbols — required for VMProtect's MAP-file-based function selection,
  used to produce the `vmprotect`-tagged release build.

## Checkpoint poison constants (for telling failures apart while testing)

`g_trust` starts at `0x5EED1234` and gets XORed with one of these per
failing checkpoint — useful for you to instrument a debug build and see
exactly which checkpoint(s) are unhappy, never exposed to a solver:

```
AEGIS_POISON_FORMAT     0x9F3A1C55
AEGIS_POISON_VM_MAC     0x2B77E081
AEGIS_POISON_INTEGRITY  0x764DAA0F
AEGIS_POISON_ANTIDEBUG  0x11FE6C93
```
